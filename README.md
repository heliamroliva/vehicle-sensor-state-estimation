# Vehicle and Sensor Estimation | Reproducible Portfolio Case

**Scope:** A nominal, synthetic longitudinal vehicle simulation. This is a software demonstration relevant to graduate systems engineering, systems integration, and verification and validation. It is **not** evidence of testing on a physical vehicle or production sensors.

## Project purpose and implemented work

The supplied source implements a longitudinal force-balance vehicle model, noisy IMU acceleration and GPS speed measurements, a two-state Kalman filter for speed and IMU acceleration bias, and recursive least squares (RLS) for aerodynamic drag area (`CdA`) and rolling resistance coefficient (`Crr`). The simulation combines these components and records a 60 s nominal run. This describes work visible in the supplied files; this package does not independently establish authorship or development dates.

The filter predicts at 100 Hz using IMU acceleration and updates with GPS at 10 Hz. Its state is `[vehicle speed, IMU bias]`. RLS uses the filter speed and bias-corrected acceleration to estimate the coefficients in `F_drive - mass × acceleration = (rho × CdA / 2) × speed² + mass × g × Crr`.

## Install and reproduce

Run from the directory containing this README. Python 3.13.15 on Windows 11 was used for verification. The only required third-party packages are NumPy and Matplotlib; the versions tested are pinned in `requirements.txt`.

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m simulations.nominal
.\.venv\Scripts\python.exe portfolio_analysis.py
```

On a Unix-like system, replace the first and executable lines with `python3 -m venv .venv` and `.venv/bin/python`. This platform was not tested here. The simulation writes to the relative `results/` directory, so run it from this package root. `portfolio_analysis.py` regenerates the PNGs, PDF, and JSON from the NPZ. The original `simulations/plot.py` is interactive and is not required for reproducible artifact generation.

## Verified nominal result

The simulation uses `np.random.seed(42)`, a 0.01 s step, constant 3000 N drive force, 100 Hz IMU sampling, and GPS updates every tenth step. This produces 6,000 truth/filter records and 600 stored GPS samples from 0.01 to 59.91 s.

Speed RMSE is `sqrt(mean((estimate - simulated_true_speed)^2))`. The GPS and filter RMSEs use **the same 600 GPS update indices**; the filter sample is taken **after** its GPS update. This run yields GPS RMSE **0.475408 m/s**, filter RMSE **0.271623 m/s**, and raw IMU-integration RMSE **3.455049 m/s** at those indices. Filter RMSE across all 6,000 steps is **0.275105 m/s**. These are single-seed simulation results, not measured field performance.

RLS does not recover the simulated coefficients in this run: final `CdA` is **0.190524 m²** versus **0.65 m²** true; final `Crr` is **0.112875** versus **0.015** true. The final estimated IMU bias is **0.118849 m/s²** versus **0.1 m/s²** true. The parameter plot on PDF page 2 shows 5–60 s to make the later trajectory readable; the full 0–60 s trajectory is preserved in `figures/parameter_estimation.png` and the NPZ.

## Limits and next validation steps

This package demonstrates only the nominal synthetic scenario. There is no real vehicle dataset, calibrated sensor characterization, hardware-in-loop test, fault injection run, or multi-seed robustness study. The original fault and validation modules were empty and are not presented as completed capabilities. The GPS sensor is sampled in an extra discarded draw each simulation step, which affects the seeded noise sequence; this source behavior was preserved for reproducibility. The RLS parameter errors indicate that identification quality needs further work before making a performance claim. A single-run mean NEES is recorded in `metrics.json` for traceability, but it is not used as a consistency conclusion.
